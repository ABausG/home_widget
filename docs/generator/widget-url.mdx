# Widget Clicks

Set `widgetUrl` on the annotation to have a tap on the widget open your app with that URL:

```dart
@HomeWidget(
  name: 'Weather',
  widgetUrl: 'myapp://weather',
  android: HomeWidgetAndroidConfiguration(),
  iOS: HomeWidgetIOSConfiguration(groupId: 'group.com.example.app'),
  widget: HWText(HWString('city')),
)
class Weather {}
```

The generator emits `.widgetURL(...)` on iOS and a Glance `clickable(actionStartActivity<MainActivity>(...))` on Android, so the same URL reaches the app on both platforms. Nothing has to be added to the native code by hand, including the Android manifest entry, which the CLI writes for you. No URL scheme has to be registered.

To open the app from one region of the widget instead of the whole widget, wrap that region in an [`HWLink`](/generator/widgets/hw-link). Links and `widgetUrl` can be combined, and both are read through the launch helpers described below.

## Sending data with the tap

`widgetUrlData` lists values the tap sends along with `widgetUrl`:

```dart
@HomeWidget(
  name: 'Weather',
  widgetUrl: 'myapp://weather',
  widgetUrlData: [
    HWString('city'),
    HWPayload('source', HWString.fixed('widget')),
  ],
  android: HomeWidgetAndroidConfiguration(),
  iOS: HomeWidgetIOSConfiguration(groupId: 'group.com.example.app'),
  widget: HWText(HWString('city')),
)
class Weather {}
```

The values are appended to the URL as percent-encoded query parameters. With `Berlin` saved as `city`, the tap opens `myapp://weather?city=Berlin&source=widget&homeWidget`.

A stored value is sent under its key, and `HWPayload(name, value)` names a fixed value or renames a stored one. See [Payloads](/generator/data#payloads) for the allowed types and the naming rules. `widgetUrlData` without a `widgetUrl` is a generation error, and so is an `HWItemData` in it, because there is no list item at the root of the widget.

The values are the ones the widget was **rendered with**, not the state at the moment of the tap.

## The generated launch model

A widget that sets `widgetUrl` or contains an `HWLink` gets a sealed class with one subclass per thing that can be tapped:

```dart
sealed class WeatherLaunch {
  /// The launch [uri] stands for, or null when it is not a URL this widget
  /// opens the app with.
  static WeatherLaunch? fromUri(Uri uri);

  /// The URL the widget opens the app with for this launch.
  Uri toUri();
}

/// A tap on the widget itself. Generated when `widgetUrl` is set.
final class WeatherWidgetTap extends WeatherLaunch {
  const WeatherWidgetTap({this.city, this.source = 'widget'});

  final String? city;
  final String source;
}

/// A tap on HWLink('forecast', ...). One class per link id.
final class WeatherForecastLink extends WeatherLaunch { ... }
```

- `<Name>WidgetTap` carries one field per `widgetUrlData` entry and has no fields without it.
- `<Name><Id>Link` carries one field per entry of the link's `data`.
- The fields are typed `String`, `int`, `double`, `bool` or `DateTime`. A date travels as an instant in UTC with millisecond precision, and two launches compare their dates that way. A field is nullable unless its value is fixed or its data type declares a `defaultValue`. See [Payloads](/generator/data#generated-fields).
- Every class has value equality and a readable `toString`.

## Reading taps in the app

The generated helper class gains two launch helpers:

```dart
/// The tap on this widget the app was started by, or null when it was
/// started any other way.
static Future<WeatherLaunch?> initialLaunch();

/// The tap that started the app first, if one did, then every tap while
/// it runs.
static Stream<WeatherLaunch> launches();
```

Listening to `launches()` covers both cases at once:

```dart
@override
void initState() {
  super.initState();
  _subscription = WeatherHomeWidget.launches().listen(_onLaunch);
}

void _onLaunch(WeatherLaunch launch) {
  switch (launch) {
    case WeatherWidgetTap(:final city):
      _openWeather(city);
    case WeatherForecastLink():
      _openForecast();
  }
}

@override
void dispose() {
  _subscription.cancel();
  super.dispose();
}
```

The switch is exhaustive because the class is sealed: a link added to the widget later is a compile error until the app handles it.

`launches()` subscribes to taps before it reads the URL the app was started with, so a tap arriving while that read is in flight is kept and not dropped.

<Info>
The launch helpers call `HomeWidget.initialLaunch` and `HomeWidget.launches`, which `home_widget` has from 0.10.1. When `pubspec.lock` resolves an older hosted `home_widget`, generation fails with a message asking you to raise the constraint.
</Info>

### Matching

A URL belongs to a launch when all of these match the URL written in the schema:

- the scheme, compared lower-cased,
- the authority (host and port),
- the path,
- the fragment,
- every query parameter written into the URL itself.

The remaining query parameters are the payload. A payload value that is missing or cannot be read decodes to `null`, or to the field's default. Query parameters the launch does not know are ignored. A URL with malformed percent-encoding is no launch at all: `fromUri` answers `null` for it.

One URL can extend another with a query parameter. The launch that writes more query parameters into its URL is matched first, so `myapp://home?tab=settings` is tried before `myapp://home`:

```dart
@HomeWidget(
  name: 'Weather',
  widgetUrl: 'myapp://home',
  widget: HWLink(
    'settings',
    url: 'myapp://home?tab=settings',
    child: HWText(HWString.fixed('Settings')),
  ),
  // ...
)
class Weather {}
```

Two things that can be tapped in one widget still need URLs the app can tell apart. Generation fails when two URLs differ only in the data they send, and when a value one of them sends can produce a query parameter written into the other, such as `data: [HWString('tab')]` on `myapp://home` next to `myapp://home?tab=settings`.

A URL has to be written the way it is opened: characters that are not allowed in a URL, such as a space, a quote or a brace, have to be percent-encoded, and generation fails for one that is not. The same goes for `[` and `]` outside an IP address host and for a second `#`, which iOS before 17 cannot open, and for a query whose percent-encoding does not decode as UTF-8, such as `%FF`.

### Filtering

Both helpers report **only taps whose URL is one this widget opens**. A URL that matches none of the widget's launches is skipped, which is why the stream is a `Stream<WeatherLaunch>` without nulls. A tap is told by its URL alone, so give every widget URLs of its own: when two widgets open the same URL, both report the tap, and `generate` warns about it.

The tap that started the app is delivered once per run of the app. After one `launches()` listener has received it, a stream listened to later, such as one a rebuilt widget subscribes to, starts with the taps that follow. `initialLaunch()` keeps answering it.

To handle the taps of several widgets in one place, call `fromUri` of each widget on the `Uri` from [`HomeWidget.initiallyLaunchedFromHomeWidget()` and `HomeWidget.widgetClicked`](/features/detect-clicks), or merge their `launches()` streams.

### Building a launch URL

`toUri()` returns the URL the widget opens the app with for a launch, and `fromUri` reads one back. That is useful in tests and for routing a launch through code that takes a `Uri`:

```dart
final uri = const WeatherWidgetTap(city: 'Berlin').toUri();
// myapp://weather?city=Berlin&source=widget&homeWidget

WeatherLaunch.fromUri(uri) == const WeatherWidgetTap(city: 'Berlin'); // true
```

## The `homeWidget` query parameter

The plugin only reports a click whose URL carries a `homeWidget` query parameter, which is how iOS tells a widget tap apart from any other URL your app is opened with. The generator appends it for you when it is not already there, on **both** platforms, so the `Uri` the app sees is identical everywhere:

```
myapp://weather        →  myapp://weather?homeWidget
myapp://weather?city=1 →  myapp://weather?city=1&homeWidget
myapp://weather#today  →  myapp://weather?homeWidget#today
myapp://weather?tab=1  →  myapp://weather?tab=1&city=Berlin&homeWidget
```

A URL that already carries the parameter is passed through untouched, and the rest of the URL is left exactly as written.

The last line is a URL with a payload, here `widgetUrlData: [HWString('city')]`. Payload values go after the query parameters the URL already has and ahead of `homeWidget`. A payload entry cannot be named `homeWidget`, or like a query parameter written into the URL.

<Info>
The generator emits the URL string verbatim into the native code, but what the app receives is a parsed `Uri`, and `Uri.parse` lower-cases the scheme. A `widgetUrl` of `myApp://weather` therefore arrives as `myapp://weather?homeWidget`. Everything after the scheme keeps its casing. The launch helpers already match the lower-cased scheme, so they need no normalization of your own.
</Info>

## Without a `widgetUrl`

Leaving `widgetUrl` off does not make the widget inert: tapping it still opens your app, matching what iOS does by default for a widget that declares no `widgetURL`. On Android the generator emits a plain `actionStartActivity<MainActivity>()` for that case. The app launches, but the intent carries no URL, so no tap is reported. The launch helpers are then generated only when the widget contains an [`HWLink`](/generator/widgets/hw-link), and report the links alone.

<Info>
If you want to detect launches, to route to a screen, log the tap, or refresh on open, set a `widgetUrl`. That is what turns the tap into something the app can read.
</Info>

<Info>
On Android the URL is delivered through an intent-filter on your launcher activity. The CLI adds it to `AndroidManifest.xml` automatically when a schema sets a `widgetUrl` or contains an `HWLink`. If it cannot find a launcher activity it warns during generation, and the URL will not reach the app until the warning is resolved.
</Info>

## Widgets that should not open the app

Set `openAppOnTap: false` on `HomeWidgetAndroidConfiguration` to leave the Android widget without a click action entirely:

```dart
@HomeWidget(
  name: 'Status',
  android: HomeWidgetAndroidConfiguration(openAppOnTap: false),
)
class Status {}
```

No `clickable(...)` modifier is emitted, no launch intent-filter is written to the manifest, and `widgetUrl`, `widgetUrlData` and every `HWLink` are ignored on Android: a tap does nothing. The generator warns when such a widget contains an `HWLink`. iOS is unaffected: its `widgetURL` and links still apply, and the launch helpers keep reporting taps there while staying silent on Android.

## When no launcher activity is found

The Android click action targets the activity your manifest declares with the `MAIN`/`LAUNCHER` intent-filter, resolving a relative `android:name` against the manifest `package` or your `applicationId`. If the generator cannot find that activity, it does not guess a class name: it warns during generation and emits the widget and its links without a click action, so the generated Kotlin never references a class that does not exist. Declare a launcher activity, or set `openAppOnTap: false` if the widget is meant to be inert, to resolve the warning.

## Uri helpers

Before 0.5.0 the generated helper class reported taps as plain `Uri`s, through a static `widgetUrl` field, `initiallyLaunchedFromWidget()`, `widgetClicked` and `launchedFromWidget()`. They were removed in 0.5.0 in favor of `initialLaunch()` and `launches()`. See [Migration to 0.5.0](/generator/migrations/0.5.0#uri-launch-helpers-removed) for the replacement of each one.
